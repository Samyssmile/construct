# Accessibility Guidelines

**Accessibility is Priority #1 in Construct.** Construct targets applicable WCAG 2.2 AA criteria through semantic markup contracts, tested headless behavior, contrast gates, visible focus, reduced motion, and high-contrast support. Product accessibility still depends on content and integration.

---

## Core Principles

### Do

- Use semantic HTML (`button`, `input`, `label`, `table`, `nav`, `main`, `aside`)
- Use design tokens for colors, spacing, typography, and border radius
- Maintain clear state logic (hover, focus, active, disabled, error)
- Use consistent sizes (sm, md, lg) for form controls and buttons
- Test all interactive functionality with keyboard navigation (Tab, Shift+Tab, Enter, Space, Arrow keys)

### Don't

- Don't rely on color alone to convey status — always add text or an icon
- Don't create custom interactive controls without ARIA roles and keyboard support
- Don't use fixed-pixel layouts for content that can grow
- Don't use low-contrast text or unreadable disabled states
- Don't add unnecessary animations for critical or irreversible actions

---

## Minimum Requirements for All Components

| Requirement | Detail |
|-------------|--------|
| **Visible Focus** | All interactive elements must have a clearly visible `:focus-visible` indicator |
| **Labels** | Every form input needs a label — explicit `<label>` or `aria-label` / `aria-labelledby` |
| **Keyboard Navigation** | All functionality must be reachable and operable by keyboard alone |
| **ARIA** | Use ARIA attributes only where semantic HTML is insufficient |
| **Contrast** | Text, icons, and focus rings must meet WCAG AA (4.5:1 normal text, 3:1 large/UI) |
| **Themes** | Support light, dark, and high-contrast modes; respect system preferences |
| **Disabled States** | Must be recognisable; content must remain readable (never invisible) |
| **Motion** | Respect `prefers-reduced-motion`; never hard-code animation durations |
| **Live Regions** | Use `aria-live` only when a dynamic update must be announced without moving focus; do not make static status text noisy |
| **Links** | Distinguish links from surrounding text without color alone (e.g. underline) |
| **Coarse pointer** | Follow Construct's 44×44 target policy for the covered compact controls |
| **Forced colors** | Preserve essential boundaries, state indicators, and visible focus |

## Component State Attributes

Prefer native and standard ARIA attributes; use documented `data-*` hooks for structural/visual states that ARIA does not express:

| State | Attribute | Example |
|-------|-----------|---------|
| Error | `aria-invalid="true"` | `<input aria-invalid="true" />` |
| Disabled | `disabled` or `aria-disabled="true"` | `<button type="button" disabled>` |
| Selected | `aria-selected="true"` | Tab, option, list item |
| Current page | `aria-current="page"` | Navigation link |
| Expanded | `aria-expanded="true\|false"` | Accordion, dropdown trigger |
| Pressed | `aria-pressed="true\|false"` | Toggle button |
| Checked | `aria-checked="true\|false\|mixed"` | Checkbox, switch |
| Loading | `aria-busy="true"` + documented visual hook | Updating region or loading button |

Always pair `aria-invalid="true"` with visible error text linked via `aria-describedby`.

## Keyboard Patterns for Composite Components

### Tabs

| Key | Action |
|-----|--------|
| Arrow keys | Move focus between tabs |
| Home / End | Jump to first / last tab |
| Enter / Space | Activate the focused tab |

**Implementation:** Use roving tabindex — the active tab has `tabindex="0"`, all others have `tabindex="-1"`.

```html
<div role="tablist">
  <button type="button" role="tab" id="tab-1" aria-selected="true"
          tabindex="0" aria-controls="panel-1">Tab 1</button>
  <button type="button" role="tab" id="tab-2" aria-selected="false"
          tabindex="-1" aria-controls="panel-2">Tab 2</button>
</div>
<div role="tabpanel" id="panel-1" aria-labelledby="tab-1">Content 1</div>
<div role="tabpanel" id="panel-2" aria-labelledby="tab-2" hidden>Content 2</div>
```

### Dropdown (Action-menu pattern)

| Key | Action |
|-----|--------|
| Enter / Space | Open dropdown; focus moves to the first enabled item |
| Arrow keys / Home / End | Move the roving focus between enabled menu items |
| Typeahead | Move to the next item whose label matches the typed prefix |
| Esc | Close dropdown; return focus to trigger |
| Tab | Close without cancelling the key, so focus continues out of the widget |

The trigger uses `aria-expanded` and `aria-controls`:

```html
<button type="button" id="menu-trigger" aria-expanded="false"
        aria-controls="menu" aria-haspopup="menu">
  Options
</button>
<ul id="menu" role="menu" aria-labelledby="menu-trigger" hidden>
  <li role="none"><button type="button" role="menuitem" tabindex="-1">Edit</button></li>
  <li role="none"><button type="button" role="menuitem" tabindex="-1">Delete</button></li>
</ul>
```

Use `createDropdownController` for this complete menu-button contract. If the content is a generic disclosure with ordinary links or controls, use the Popover pattern and keep native elements in their natural Tab order instead of adding menu roles.

### Datepicker

| Key | Action |
|-----|--------|
| Arrow keys | Move focus by day in the calendar grid |
| Page Up / Page Down | Switch months |
| Home / End | Jump to start / end of week |
| Enter / Space | Select the focused date |
| Esc | Close calendar; return focus to trigger |

### Modal / Dialog

| Key | Action |
|-----|--------|
| Esc | Close modal |
| Tab | Move focus forward within modal (trapped) |
| Shift+Tab | Move focus backward within modal (trapped) |

**Requirements:**
- Set `role="dialog"` and `aria-modal="true"` on the inner dialog element, not its backdrop
- Set `aria-labelledby` pointing to the modal's heading
- On open, move focus to the first focusable element (or a designated element)
- Trap focus — Tab and Shift+Tab must not leave the modal while it is open
- On close, return focus to the element that triggered the modal

```html
<div role="dialog" aria-modal="true" aria-labelledby="modal-title">
  <h2 id="modal-title">Confirm deletion</h2>
  <p>This action cannot be undone.</p>
  <button type="button">Cancel</button>
  <button type="button">Delete</button>
</div>
```

### Tooltip

| Event | Action |
|-------|--------|
| Hover / Focus | Show tooltip |
| Mouse leave / Blur | Hide tooltip |
| Esc | Hide tooltip |

```html
<button type="button" aria-describedby="tip-save">Save</button>
<div role="tooltip" id="tip-save">Saves your work (Ctrl+S)</div>
```

### Accordion

| Key | Action |
|-----|--------|
| Enter / Space | Toggle panel open / closed |
| Tab | Move to next interactive element |
| Shift+Tab | Move to previous interactive element |

```html
<h3>
  <button type="button" aria-expanded="false" aria-controls="panel-1">
    Section title
  </button>
</h3>
<div id="panel-1" hidden>Panel content</div>
```

## Focus Management

Use the public controllers instead of copying a partial focus trap or roving-tabindex snippet. They handle
disabled items, RTL/orientation, nested overlays, Escape, outside interaction, focus return, and cleanup.

```js
import {
  createModalController,
  createTabsController,
} from '@neuravision/construct/behaviors';

const modal = createModalController({ container, dialog, trigger });
const tabs = createTabsController({ tablist, activation: 'automatic' });

// On framework/view cleanup:
modal.destroy();
tabs.destroy();
```

Use the matching controller for Drawer, Toggle Group, Dropdown, Select Menu, Combobox, Tooltip, and
Popover. Rendering and product data remain application responsibilities.

## Live Regions

Use a live region when a dynamic update such as an important toast, status message, or progress milestone
must be announced without moving focus. Do not mirror every visual update or add `aria-live` to static
labels; repeated or low-value announcements make the interface harder to use.

```html
<!-- Polite: announces after current speech finishes -->
<div aria-live="polite" aria-atomic="true" class="ct-sr-only" id="status-region"></div>

<!-- Assertive: interrupts immediately (use sparingly for critical errors) -->
<div aria-live="assertive" aria-atomic="true" class="ct-sr-only" id="alert-region"></div>
```

```js
function announce(message, priority = 'polite') {
  const region = document.getElementById(
    priority === 'assertive' ? 'alert-region' : 'status-region'
  );
  region.textContent = '';
  requestAnimationFrame(() => { region.textContent = message; });
}

// Usage
announce('File uploaded successfully');
announce('Session expired — please log in again', 'assertive');
```

## Screen Reader Only Text

Visually hide supplementary text that only screen readers need:

```css
.ct-sr-only {
  position: absolute;
  width: 1px;
  height: 1px;
  padding: 0;
  margin: -1px;
  overflow: hidden;
  clip: rect(0, 0, 0, 0);
  white-space: nowrap;
  border: 0;
}
```

```html
<!-- Icon-only button with accessible label -->
<button class="ct-button ct-button--icon" type="button" aria-label="Close dialog">
  <span aria-hidden="true">✕</span>
</button>

<!-- Table with supplementary context -->
<td>
  98%
  <span class="ct-sr-only">uptime last 30 days</span>
</td>
```

## Testing Checklist

Before merging any new component, verify:

- [ ] All interactive elements are reachable and operable by keyboard
- [ ] Focus indicator is visible on all interactive elements (`:focus-visible`)
- [ ] All images have `alt` text; decorative images have `alt=""`
- [ ] All form inputs have associated `<label>` elements
- [ ] Color is not the sole means of conveying information
- [ ] Contrast ratios pass WCAG AA (4.5:1 for body text, 3:1 for large text/UI)
- [ ] Component works correctly in dark, high-contrast, and forced-colors modes
- [ ] Covered compact controls meet the 44×44 coarse-pointer policy
- [ ] Required dynamic announcements are delivered once at the appropriate live-region priority; static updates remain quiet
- [ ] Modals trap focus and restore focus on close
- [ ] No accessibility violations in the Storybook a11y panel

### Automated testing

The Storybook a11y addon (powered by axe-core) runs on every story and is configured to **fail CI on violations**. Run it locally with:

```bash
npm run check
npm test
```

## Fonts and Typography

`foundations.css` makes no network request. Products can use the resilient fallback stack, explicitly
opt into hosted fonts with `fonts.css`, or self-host licensed files. See `docs/fonts.md` for weights,
privacy/CSP guidance, and override examples.

## Governance

- **New components require:** owning token layer, state definitions, accessibility notes, and a Storybook story
- **Before merge:** `npm run check`, `npm test`, Storybook build, visual/keyboard/screen-reader review
- **Review process:** at least one accessibility review for new interactive components
